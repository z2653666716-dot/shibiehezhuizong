# 身份保持实验版：使用与验收

## 分支和入口

`main`保存已验证的0.2.2诊断版本，`v0.2.1-baseline`固定更早可运行基线。新方法只在`feature/face-assisted-reid`；当前尚未完成用户实拍验收，不直接合入main。

```text
app/main.py                 后端入口
app/pipeline.py             串联检测、跟踪、身份与照片接口
app/hybrid_session.py       新的身份保持与单目标状态
app/faces.py                人脸检测、质量与专用特征
app/person_features.py      行人ONNX模型
app/onnx_backend.py         旧导出图规范与实际执行器
app/tracker.py              ByteTrack或BoT-SORT关联
scripts/run_identity.ps1    实验启动入口
scripts/analyze_tracking.py 匿名原因链路分析
tests/test_hybrid_identity.py 合成规则与真实公开样例回归
```

## 模块怎样协作

1. `Pipeline`收到一帧，在已有处理锁中调用YOLO，实验模式再做YuNet人脸检测；只见清晰人脸而没有人物框时，用实际人脸检测分数补充`person-face`观测，不能伪造YOLO结果。
2. `Tracker`的BoT-SORT使用位置、相机运动与OSNet行人外观关联轨迹。图像只在内存，灰度历史在重置时清除；新轨迹号本身不是确认身份的证据。
3. `FaceEncoder.read`拒绝过小、模糊和角度极端的人脸特征。不可靠的脸表示“缺少观测”，不是“确定另一个人”。只有唯一归属的人脸能用于对应人物；尚无轨迹号的新白框也参与归属歧义判断。
4. `HybridSession.evidence`分别判断可靠人脸、行人外观和连续运动。已有目标在正常姿态/尺度变化时可使用行人证据连续跟踪；身体也不足时仅短暂等待。清晰人脸明显冲突、多人归属不明、轨迹中断时不盲目继承身份。已有脸模板的目标离开后，新轨迹必须重新通过人脸确认。
5. 新模板只在可靠确认后有限增加。清晰人脸确认后可以补充该人的新身体姿态；远处登记时没有可用脸，需持续的很强行人证据且脸归属唯一才补充第一份脸模板。取消、删除、停止会话清除这些内存。

只有头部的照片和画面不会被当作全身输入。已经确认的头部目标在侧脸状态下仍有持续脸部位置观测、运动连贯且无人交叠时，可以维持`continuity`，不会要求侧脸复现正脸模板；可靠正脸明确冲突、轨迹中断或多人归属不明时重新确认。头部观测不拿去更新全身模板，也不依据低相似度的连续跟踪去学习新的人脸。

`verification=face/body/continuity`说明当前依据；`continuity`只表示连续跟踪，人脸此刻尚未重新确认，不是身份认证结论。

## 如何启动

依赖与3份模型已在当前电脑准备；重新解压或换电脑时才需要安装依赖并运行下载脚本：

```powershell
.\envs\vitrack\python.exe -m pip install -r requirements.txt
.\envs\vitrack\python.exe -X utf8 scripts/fetch_identity_models.py
```

启动实验版，不修改原来的`.env`，不自动打开摄像头：

```powershell
# 本机网页：只启动服务，用户手动开启采集
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_identity.ps1 -Mode pc -Port 8445

# 手机使用电脑热点：先确认热点已开启，手机已连接；证书须包含当前热点IP
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_identity.ps1 -Mode phone -Port 8445 -LanIP 192.168.137.1
```

手机网址以终端实际输出为准。热点未开启、IP不再属于电脑时启动检查应拒绝；不要用旧IP绕过检查。`-CheckOnly`只校验，不加载模型或打开设备。停止服务按Ctrl+C。

## 现场验收顺序

重新取得本次摄像头及内存人脸特征处理授权后，用户手动开始、停止；不保存或外传照片、视频、截图、裁剪、向量。请先看“照片登记与匹配”，确认照片登记是否成功。

1. 清晰单人人脸照片登记，用户入镜，不手动长按，应自动出现同一ID的绿框。
2. 在一次连续画面内正常转头、侧脸和改变姿势，观察是否保持同一ID及何时使用“跟踪中”。
3. 从远处登记后逐渐走近；再从近处逐渐走远。过小脸无法提供有效人脸特征时如实记录。
4. 离开10秒再回来，记录恢复同一ID需要多久；两人交叉时检查是否误绑。每位参与者应同意测试。
5. 白框轻点变黄，再长按应只执行一次；再长按绿框只取消一次。取消后不能自动恢复。
6. 完成后停止检测，确认浏览器摄像头提示结束。文字反馈即可，不需要截图或传照片给聊天。

这些情况仍需实际测试。合成向量验证的是状态规则，公开样例的缩放与同图裁剪不等于真正的跨姿态、跨时间重识别成绩。

## 安卓选择照片与页面返回

手机系统相册可能暂时让网页进入后台。旧页面在这一步直接断开视频会话，清掉文件输入，导致照片还未上传就丢失登记条件。修复后，只有用户主动点击“上传照片”的流程享有最多60秒的相册等待时间；相册遮住页面时禁用原视频轨道、停止取帧和传帧，短暂保留原连接。回到页面后恢复仍存活的同一轨道，不重新申请或自动开启新设备。

照片结果和“网页已返回前台”可能按不同顺序到达，两种顺序都应使用同一个会话。取消相册会恢复按钮；上传网络失败、超时或返回内容不正确会显示常驻中文原因。选照超时仍在后台，或返回时发现期限已过，检测会停止；用户需要手动重新开始。普通切后台、关闭网页和点击停止仍按原清理流程执行。

本次主要阅读位置：`interaction.js`的`beginPhotoSelection`先记录选照状态，`uploadPhoto`接收文件并等待真实接口结果；`app.js`的`handleVisibility`根据页面隐藏/显示决定暂停或恢复；`camera.js`的`pauseCapture/resumeCapture`只操作当前仍有效的视频轨道。停止时取消在途上传，旧请求不能覆盖后来会话的界面。

`PHOTO_PICKER_TIMEOUT_MS=60000`是相册等待上限，上传请求另有30秒上限。延长前者会让后台内存会话保留更久，不会提高识别成功率；保持默认即可。选择JPEG或PNG照片，文件小于6MiB。网页刷新即可取得这次前端修复，不必重新加载后端模型。

2026-10-19用户已完成本次安卓复测，文字确认“登记成功，入镜后自动变绿”，并确认“已停止，摄像头提示已结束”。因此照片选择、登记、首次自动匹配与停止释放这条路径已有一次现场通过记录；本次未报告识别耗时、侧脸/姿态/远近表现或其他手机兼容性，不扩大验收结论。

## 参数与限制

- `FACE_MATCH_THRESHOLD=0.45`：新的人脸匹配门槛；未用用户现场数据标定。提高更谨慎但可能增加漏认。
- `BODY_MATCH_THRESHOLD=0.75`、`BODY_HOLD_THRESHOLD=0.55`：新行人模型用于重新确认与连续维持的不同门槛，不与旧MobileNet的0.90直接比较。
- `IDENTITY_HOLD_SECONDS=2`：可靠观测缺失时最多短暂等待，不能无限沿用旧身份。
- 人脸模板和身体模板最多各`REID_MAX_TEMPLATES`份。重复相似模板不反复加入，最初人脸模板保留。
- `IDENTITY_DEVICE=cpu`为本机实测后的默认；YOLO仍在GPU。已有绑定时每3帧做一次人脸特征，其间不复用旧脸向量。行人特征只缓存同一帧的相同裁剪，停止后清除，避免运动层与身份层重复前向。
- 原模型声明固定batch=16，运行前仅改为动态batch并冻结旧图的权重输入，原文件SHA256不变。原图与规范图的数值一致性已验证；不再为一个人计算15份填充。
- CPU原图公开640样例为9.803FPS，CUDA原图更慢为4.224FPS；动态批CPU同样例20帧为12.636FPS，平均78.69ms，仍未达到原15FPS目标。这些是固定图多人处理吞吐，不是手机实时数据。当前优先验证身份保持，性能限制如实保留。
- OSNet候选模型的训练资料有限，来源限制见`third_party.md`。当前准确率、正常侧脸范围与真实手机FPS尚未标定或验收，不能承诺所有角度和距离都成功。

阅读建议：先看本文件，再看`pipeline.py`的实验分支，随后看`hybrid_session.py`的`evidence`和`remember_confirmed`，最后看两个编码器与测试。不要靠不断降低门槛制造“全部变绿”。
