# 功能分支与集中验收

## 固定的开发基线

用户指定基线为原8446服务的`0.3.1-experimental`，提交`2b6ea26`。

- GitHub分支：`baseline/user-tested-v0.3.1`。
- 固定标签：`v0.3.1-user-baseline`。
- 已有人工反馈：照片登记、本人入镜自动变绿、两人同框轻微移动通过；侧脸本次反馈没有明显问题。
- 已知不足：姿态变化及远近移动会丢失，重入/交叉和准确率没有完整验收。基线表示可以回退的起点，不代表所有问题已解决。

后续分支按依赖顺序派生。B分支包含A的代码，再新增B；切换任一分支都能运行，无须先把它合入main。集中测试时，按“上一版→下一版”观察新增功能的差别。分支合并顺序同派生顺序，当前保留待用户决定。

## 分支A：人脸与人物框归属

- 分支：`fix/face-association`；父分支：`baseline/user-tested-v0.3.1`。
- 页面运行版本：`0.3.2-face-association`。
- 核心文件：`app/faces.py`的`FaceEncoder.associate`，输入人脸位置与人物框，输出只有唯一解释的“轨迹号→人脸”关系，不使用身份分数猜归属。
- 人脸都在两个身体框内而没有唯一解释时仍拒绝分配；新白框即使没有轨迹号也参与约束。不能把两张脸都分给一个身体。
- 待集中观察：两人靠近、身体框交叠但脸分别可见时，是否更少反复进入识别中；真正交叉时是否误锁旁人。
- 自动检查：归属/真实模型10项通过；真实照片页面与PWA另2项通过。手机现场验收仍待用户集中进行。

## 分支B：短时轨迹恢复

- 分支：`fix/brief-track-recovery`；父分支：`fix/face-association`，包含A。
- 页面运行版本：`0.3.3-track-recovery`。
- `HybridObservation`只在内存保存最近真实位置、时间和确认进度；`HybridSession.update`在同一BoT-SORT轨迹漏检最多2帧、返回位置连贯且时间未超限时恢复进度。当前身份与人脸仍重新检查，缺失帧不增加成功次数。
- 超过2帧、位置不连贯、太久没有真实观测或出现换人证据时重新确认；不会给已经消失的人补画预测绿框。
- 自动检查：候选/真实模型/跟踪共22项通过。
- 待集中观察：坐下站起、姿态变化中短暂漏检后是否更快恢复原身份；长时间离开后不能直接把新入镜者沿用为原目标。

## 分支C：身体依据的有期限等待

- 分支：`fix/body-overlap-continuity`；父分支：`fix/brief-track-recovery`，包含A/B。
- 页面运行版本：`0.3.4-body-continuity`。
- `evidence`比较当前目标、同帧旁人的身体分数及登记时反例。原轨迹运动连贯、身体可靠且明显领先旁人时，脸归属暂时不清可以维持最多原配置的2秒等待，输出“跟踪中”。等待不会刷新可靠确认时间。
- 新白框或缺少身体特征的交叠人物不能被当作已经比较并输给目标；可靠异人脸、多人分数相近、等待超时仍撤绿。
- 自动检查：候选、模型、页面、状态诊断和单目标共28项通过。
- 待集中观察：姿态变化造成短暂人脸归属困难时是否少撤绿；相同衣服的另一人靠近时是否误锁。真实结果未提前标为通过。

## 分支D：远处身体锁定后补充人脸

- 分支：`fix/distant-face-enrollment`；父分支：`fix/body-overlap-continuity`，包含A/B/C。
- 页面运行版本：`0.3.5-face-enrollment`。
- `remember_confirmed`在初始只登记身体、随后走近时，累计6份互相一致的清晰正脸。每三帧主动跳过的特征前向只保留进度，不加次数。身体还须强匹配并明显领先旁人。
- 临时首份脸向量`face_seed`只在会话内存；新脸与它不一致就重新计数，取消、删除和停止清除。已有脸模板的目标继续沿用原有限模板规则。
- 待集中观察：远处长按身体锁定后慢慢走近，随后正常转头与姿态变化是否更稳定；脸太小或模糊时不能宣称已经建立人脸模板。
- 完整自动回归87项通过，包含A/B/C/D、照片选择流程、真实公开模型、接口、浏览器、PWA与保存限制。现场验收仍待用户集中进行。

## 派生和比较顺序

```text
baseline/user-tested-v0.3.1  原8446基线，2b6ea26
  └─ fix/face-association                 A，人脸归属
      └─ fix/brief-track-recovery         B，短漏检恢复
          └─ fix/body-overlap-continuity  C，身体依据等待
              └─ fix/distant-face-enrollment  D，走近补充人脸
```

先测试基线，再按A/B/C/D比较新增效果。每个分支保留自己的版本标记、自动验证记录和完整可运行代码。有依赖关系时，后一个分支包含前一个；不需要先合并main才能启动。待用户集中测试后，按同一顺序决定保留或合并。测试发现问题时只反馈对应版本和动作，方便针对该功能继续修复。

## 最后集中测试时如何切换

以下命令由用户准备集中测试时运行；代码交付期间不需要现在开启相机。首次使用空闲8450端口时，可以保留后台的基线8446服务。后续切换版本前，先停止手机检测，再在自己新开的8450服务终端按Ctrl+C，关闭该测试服务。

```powershell
git status --short
git switch fix/face-association
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_identity.ps1 -Mode phone -Port 8450 -LanIP 192.168.137.1
```

`git status --short`若列出自己未提交的修改，先保留修改再切分支，不使用强制切换。启动前打开电脑移动热点，手机连接，确认热点网关仍为192.168.137.1；地址变更时按实际地址和证书检查处理。

手机访问`https://192.168.137.1:8450`并刷新，查看页面顶部“运行版本”是否符合所选分支。Git切换只改变磁盘文件，不会让旧Python进程换版本，所以必须停止并重新启动服务。8450只是集中验收时建议统一使用的空闲端口，不等于当前后台8446已升级。

下一版只需将`git switch`后的名称按A/B/C/D顺序替换，继续使用同一个8450端口，避免手机混用旧网址。若最终要返回用户指定基线，切换`baseline/user-tested-v0.3.1`后重新启动测试服务。

## 统一记录的测试项目

1. 照片登记：清晰的本人单人照登记成功，入镜后不长按是否自动变绿。
2. 姿态与距离：坐下站起、正常转身、慢慢走近和走远，观察绿框、身份号及恢复情况。记录哪个动作失败，不只写“效果不好”。
3. 多人：第二人靠近、并排、短暂交叉，观察是否保持本人，是否误锁另一人。两位都须同意本次测试。
4. 远处手动登记：先在较远位置长按本人身体框，再走近让正脸清晰片刻，随后正常变换姿势；此项主要比较D新增的人脸补充。
5. 离开与重入：离开10秒再回来，记录是否自动恢复相同身份；短漏检恢复不代表长时间重入已通过。
6. 取消与停止：长按绿框取消后不能自动恢复；停止检测后预览和摄像头提示都结束。IP模式还需手动停止手机App。

每个版本用同一组项目比较，脸太小、模糊或真实遮挡时如实记录。每次仅保留文字和数值，不要求录制、截图或保存特征。可按“版本、照片登记、姿态、距离、多人、误锁、重入、取消、停止”的顺序写一行反馈。

每次由用户手动开始、停止，事先取得所有参与者同意；仅在本机会话内存处理照片、画面和有限特征，不保存或向互联网传输，不用麦克风。停止后确认摄像头提示结束。记录文字结果即可：所用分支/页面版本、动作、绿框或识别中、是否误锁旁人、恢复情况、停止状态。

## 阅读顺序和参数

先读本文件了解分支，再读`tracking_upgrade.md`理解身份流程，最后看当前分支的源码和对应测试。程序入口仍为`app/main.py`，实验启动入口为`scripts/run_identity.ps1`。本次拆分不调整人脸/身体匹配门槛，保持默认参数，便于集中比较每项修改的影响。
