# 功能分支与集中验收

## 固定的开发基线

用户指定基线为原8446服务的`0.3.1-experimental`，提交`2b6ea26`。

- GitHub分支：`baseline/user-tested-v0.3.1`。
- 固定标签：`v0.3.1-user-baseline`。
- 已有人工反馈：照片登记、本人入镜自动变绿、两人同框轻微移动通过；侧脸本次反馈没有明显问题。
- 已知不足：姿态变化及远近移动会丢失，重入/交叉和准确率没有完整验收。基线表示可以回退的起点，不代表所有问题已解决。

后续分支按依赖顺序派生。B分支包含A的代码，再新增B；切换任一分支都能运行，无须先把它合入main。集中测试时，按“上一版→下一版”观察新增功能的差别。分支合并顺序同派生顺序，当前保留待用户决定。

## 分支A：人脸与人物框归属

- 分支：`fix/face-association`；父分支：`baseline/user-tested-v0.3.1`。
- 页面运行版本：`0.3.2-face-association`。
- 核心文件：`app/faces.py`的`FaceEncoder.associate`，输入人脸位置与人物框，输出只有唯一解释的“轨迹号→人脸”关系，不使用身份分数猜归属。
- 人脸都在两个身体框内而没有唯一解释时仍拒绝分配；新白框即使没有轨迹号也参与约束。不能把两张脸都分给一个身体。
- 待集中观察：两人靠近、身体框交叠但脸分别可见时，是否更少反复进入识别中；真正交叉时是否误锁旁人。
- 自动检查：归属/真实模型10项通过；真实照片页面与PWA另2项通过。手机现场验收仍待用户集中进行。

## 分支B：短时轨迹恢复

- 分支：`fix/brief-track-recovery`；父分支：`fix/face-association`，包含A。
- 页面运行版本：`0.3.3-track-recovery`。
- `HybridObservation`只在内存保存最近真实位置、时间和确认进度；`HybridSession.update`在同一BoT-SORT轨迹漏检最多2帧、返回位置连贯且时间未超限时恢复进度。当前身份与人脸仍重新检查，缺失帧不增加成功次数。
- 超过2帧、位置不连贯、太久没有真实观测或出现换人证据时重新确认；不会给已经消失的人补画预测绿框。
- 自动检查：候选/真实模型/跟踪共22项通过。
- 待集中观察：坐下站起、姿态变化中短暂漏检后是否更快恢复原身份；长时间离开后不能直接把新入镜者沿用为原目标。

## 最后集中测试时如何切换

以下命令由用户准备集中测试时运行；代码交付期间不需要现在开启相机。先停止手机检测，并在当前服务的电脑终端按Ctrl+C停止旧服务。

```powershell
git status --short
git switch fix/face-association
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_identity.ps1 -Mode phone -Port 8450 -LanIP 192.168.137.1
```

`git status --short`若列出自己未提交的修改，先保留修改再切分支，不使用强制切换。启动前打开电脑移动热点，手机连接，确认热点网关仍为192.168.137.1；地址变更时按实际地址和证书检查处理。

手机访问`https://192.168.137.1:8450`并刷新，查看页面顶部“运行版本”是否符合所选分支。Git切换只改变磁盘文件，不会让旧Python进程换版本，所以必须停止并重新启动服务。8450只是集中验收时建议统一使用的空闲端口，不等于当前后台8446已升级。

每次由用户手动开始、停止，事先取得所有参与者同意；仅在本机会话内存处理照片、画面和有限特征，不保存或向互联网传输，不用麦克风。停止后确认摄像头提示结束。记录文字结果即可：所用分支/页面版本、动作、绿框或识别中、是否误锁旁人、恢复情况、停止状态。

## 阅读顺序和参数

先读本文件了解分支，再读`tracking_upgrade.md`理解身份流程，最后看当前分支的源码和对应测试。程序入口仍为`app/main.py`，实验启动入口为`scripts/run_identity.ps1`。本次拆分不调整人脸/身体匹配门槛，保持默认参数，便于集中比较每项修改的影响。
